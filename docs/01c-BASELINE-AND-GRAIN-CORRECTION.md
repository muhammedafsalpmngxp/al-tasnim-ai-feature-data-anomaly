# Correction — Planning Baseline and Table Grain

Business input received 2026-09-07:

> `start_date` / `end_date` are generated by **P6 software**. `target_start` / `target_end`
> are set by a **human planner (an engineer)**. **We mainly look at target.**

That single fact invalidated several numbers in `01-DISCOVERY-FINDINGS.md` and
`01b-DOMAIN-ANALYSIS.md`. Verified by `others/discovery/16_p6_vs_target.py` and
`17_grain_check.py`. This document is the correction and the reason it happened.

---

## 1. Two independent errors were in my earlier figures

### Error A — wrong baseline

I compared things against P6 dates (`startDate`/`endDate`) or against whichever pair was
convenient. The business watches **target**. The difference is not cosmetic:

| Delay measured over the same 83,076 finished tasks | Late | On plan | Early |
|---|---|---|---|
| **against `target_end`** (correct) | **4,316** | **71,619** | 7,141 |
| against `endDate` — P6 (wrong) | 23,628 | 32,892 | 26,556 |

**Using P6 as the baseline reports 5.5× more late tasks.** 86% of tasks land *exactly* on
target. A report built on the P6 baseline would have told the business it was failing when
it is largely on plan.

The two plans are genuinely different documents, not copies:

| | Rows (of 107,483) |
|---|---|
| P6 and target identical (both dates) | 41,996 (39%) |
| `target_start` later than P6 | 28,219 |
| `target_start` earlier than P6 | 19,078 |
| `target_end` later than P6 | 39,114 |
| `target_end` earlier than P6 | 25,759 |

Average span: **P6 58 days, target 114 days.** The planner roughly doubles P6's durations.

### Error B — wrong grain

`well.task_daily` is a **daily progress log**, not a task list. 107,309 rows cover 35,444
distinct `(task_code, well_id)` tasks — **3.03 rows per task**, one per day worked.

Proof, one task's full history:

| ActionOn | task_code | progress | completed |
|---|---|---|---|
| 2025-11-23 | `HUP1780-29437` | 1.0000 | **False** |
| 2025-11-24 | `HUP1780-29437` | 1.0000 | **False** |
| 2025-11-25 | `HUP1780-29437` | 1.0000 | **True** |

The task reached 100% on the 23rd and was signed off on the 25th. The first two rows are
**correct history**, not contradictions. I counted them as defects.

## 4. New genuine findings this pass produced

Correcting the baseline did not reduce the finding count — it redirected it. These are real
and were invisible before.

### 4.1 Target dates that break the master date — the biggest finding yet

§4 requires construction to finish before `ex_rig_on_date`. Comparing every task's
`target_end` against its well's `ex_rig_on_date`:

| | Value |
|---|---|
| Tasks compared | 85,159 |
| **`target_end` after `ex_rig_on_date`** | **39,991** |
| **Wells affected** | **449 of 814 (55%)** |
| Worst overrun | **5,459 days** |

The planner has committed 40,000 tasks to finish *after* the rig is contractually due on
the well, across 55% of the portfolio. This is a business-rule violation measured on the
authoritative column, and it is exactly the class the feature exists to surface.

### 4.2 Progress reverses, and completion un-completes

Comparing consecutive daily rows per task:

| Transition | Occurrences | Tasks affected |
|---|---|---|
| **`progress` decreased** | **4,697** | 2,279 |
| **`completed` went 1 → 0** | **2,181** | 2,123 |

Worst progress drop is **−1.0000** — a task at 100% back to 0%. A signed-off task
un-completing 2,181 times is a workflow or sync defect, not history.

### 4.3 The daily log is itself duplicated

`(task_code, well_id, ActionOn)` should be unique for a daily log. It is not:

| | Value |
|---|---|
| Duplicate groups | **22,628** |
| Excess rows | **23,789 (22%)** |
| Worst group | 4 rows |

So there are two layers of duplication: the legitimate one-row-per-day history, and 23,789
genuinely redundant rows on top of it.

### 4.4 A phantom well with a 45-year task

|---|---|---|---|---|
| `MSSF1180-00000` | **0** | 2026-02-17 | **2071-03-24** | **16,471 d** |

`well_id = 0` is not a well. These carry 45-year and 33-year task spans and pollute every

### 4.5 `committed_start` / `committed_end` is a third planning layer

52.6% populated, and distinct from both others:

## 5. Why this happened, and the fix

**Cause:** I inferred column meaning from names and types instead of asking who writes each
column. `startDate`, `target_start` and `committed_start` are all "a start date" to a
profiler; they are three different documents to the business.

**Fix — two mandatory declarations on every check.** Neither has a default; a check that
omits either fails registration, so this cannot silently recur.

```python
@check(
    id="ACT-001",
    grain=Grain.LATEST_PER("task_code", "well_id", order_by="ActionOn DESC, id DESC"),
    baseline=Baseline.TARGET,        # PLANNER-owned. Never P6.
    business_rule_ref="§4",
)
```

| Declaration | Options | Purpose |
|---|---|---|
| `grain` | `ROW`, `LATEST_PER(...)`, `SNAPSHOT_PINNED`, `AGGREGATE` | stops history being counted as defects |
| `baseline` | `TARGET`, `P6`, `COMMITTED`, `MASTER_DATE`, `NONE` | stops the wrong plan being the yardstick |

Plus a **column-ownership register** (`config/column_semantics.yaml`) recording, for every
date and progress column: who writes it, what it means, and whether it is authoritative.

```yaml
well.task_daily:
  startDate:      { owner: P6,      role: machine_plan,  authoritative: false }
  endDate:        { owner: P6,      role: machine_plan,  authoritative: false }
  target_start:   { owner: planner, role: commitment,    authoritative: true  }
  target_end:     { owner: planner, role: commitment,    authoritative: true  }
  committed_start:{ owner: unknown, role: display_only,  authoritative: false }
  committed_end:  { owner: unknown, role: display_only,  authoritative: false }
  actual_start:   { owner: site,    role: actual,        authoritative: true  }
  duration:       { owner: P6,      role: derived_from: [startDate, endDate]  }
  progress:       { owner: site,    role: measure,       authoritative: true  }
  completed:      { owner: site,    role: signoff,       authoritative: true  }
```

Every finding in the report then prints its baseline and grain, so a reader can see what it
was measured against. A number without that context is a number nobody should trust.

**Reporting rule:** where P6 and target disagree, that is normal re-planning and is reported
as **information**, never as a defect. Only target-vs-actual and target-vs-master-date
comparisons produce delay findings.

## 7. Addendum (Phase 2, 2026-09-07) -- the same lesson, now enforced by the framework

Building the check framework surfaced one more instance of exactly this class of error,
caught the same way: by cross-checking a fresh number against an independent query before
trusting it.

`BIZ-107` (task target past the well's master date) and `BIZ-108` (rig off, tasks still
open) initially reproduced this document's Section 4.1 and 01-DISCOVERY-FINDINGS.md Class 1
figures almost verbatim -- 39,991 tasks / 449 wells, and 40,127 open tasks / 422 wells. Both
were measured **per row** against `well.task_daily`, which is a daily log at 3.03 rows per
task (Section 2 above). Once the checks were wired to run against `at_grain()` -- the
table's declared `latest_per(well_id, task_code)` grain -- the same two checks produced:

| Check | Per-row (repeats this doc's earlier figures) | Per-task (current framework) |
|---|---|---|
| BIZ-107 -- target past master date | 39,991 tasks / 449 wells | **14,003 tasks / 444 wells** |
| BIZ-108 -- rig off, tasks open | 40,127 open tasks / 422 wells | **2,768 open tasks / 370 wells** |

Both re-verified with an independently written query before being accepted (not just trusted
because the framework produced them) -- see `backend/tests/test_check_framework.py` for the
registration-level guards, and the live cross-check that produced this table.

**This is not a second bug in the same place -- it is the first one recurring in new code,
caught this time in minutes instead of a full conversation.** The framework built in
response to Section 5 (`grain` is a mandatory, validated declaration on every check) is
exactly what caught it: `BIZ-107`/`BIZ-108` were written against `well.task_daily`'s
correctly-declared `latest_per` grain from the start, so the corrected figures are what the
framework produced on its first real run -- the per-row numbers above only exist as a
sanity check confirming the earlier discovery figures really were the per-row
overstatement this document already diagnosed, not a new, independent error.

The `docs/01-DISCOVERY-FINDINGS.md` and `docs/01c` Section 4.1 figures (39,991 / 449,
40,127 / 422) should be read as **historical evidence of the mistake**, not as this
feature's current output -- the live figures above are what a report generated today
would show.

## 6. Open questions this raised

1. ~~**What is `committed_start`/`committed_end`?**~~ **RESOLVED 2026-09-07 — business
   decision: meaning not yet confirmed. Treat as `role: display_only`.** It is shown in the
   report and in the UI as "Commit", and is sortable, but **no delay, variance or compliance
   check may use it as a baseline** until the business confirms its meaning. `Baseline.COMMITTED`
   is therefore registered but disabled: any check declaring it fails registration with
   "baseline COMMITTED is not confirmed — use TARGET". Only two integrity checks run on it
   (`committed_start <= committed_end`, and start-without-end), because those hold regardless
   of what it means. Measured: 0 inversions, 4 start-without-end.
2. **Should `progress` reversals and `completed` 1→0 be flagged?** 2,181 un-completions
   could be legitimate rework (punch points reopened) or a sync defect. The business needs
   to say which — the check is easy, the interpretation is not.
3. **Is `well_id = 0` a placeholder or a bug?** Two task_codes suffixed `-00000` carry
   45-year spans.
4. **Are the 23,789 duplicate `(task_code, well_id, ActionOn)` rows expected?** Multiple
   entries per task per day — different crews reporting separately, or a double-write?
5. **`target_end` after `ex_rig_on_date` on 449 wells.** Is this accepted practice (the
   master date slips and targets are not re-baselined), or a genuine planning failure? The
   answer decides whether this is the report's headline or a known-and-accepted note.
